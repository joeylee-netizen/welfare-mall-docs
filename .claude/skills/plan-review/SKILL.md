# /plan-review — 기획 내용 검증

## 설명
기획 문서의 **내용적 품질**을 검증한다.
`/plan-validate`(구조/형식 검증)와 달리, 정책 완결성, 문서 간 정합성, 흐름 누락을 검토한다.

## 사용법
```
/plan-review BO-PDM-001                # 특정 문서 검증
/plan-review domains/BO/product        # 도메인 전체 검증 (도메인 간 연관성 포함)
/plan-review domains/BO/product --no-cross-domain  # 도메인 간 연관성 제외
```

## /plan-validate 와의 차이

| 항목 | /plan-validate | /plan-review |
|------|---------------|-------------|
| 초점 | 구조/형식 | 내용/품질 |
| 검증 예시 | 필수 필드 존재, ID 형식 | 예외 케이스 누락, 데이터-컬럼 불일치 |
| 자동화 | 규칙 기반 (기계적) | 맥락 기반 (분석적) |

## 검증 항목

### 1. 정책 완결성

Policy 문서가 비즈니스 규칙을 충분히 정의했는지 검토한다.

#### 검사 항목
- [ ] 각 규칙에 **정상 흐름**이 명시되어 있는지
- [ ] 각 규칙에 **예외 케이스**가 정의되어 있는지 (최소 1건)
- [ ] `conditions` 조건이 구체적인지 (모호한 표현 탐지: "적절한", "필요 시", "등")
- [ ] 적용 범위(대상 사용자, 시스템)가 명확한지
- [ ] 수량/금액/기간 관련 규칙에 **경계값**이 정의되어 있는지 (최소, 최대, 초과 시)
- [ ] 정책 간 **우선순위 충돌**이 없는지 (동일 상황에 상반된 규칙)

#### 모호 표현 탐지 패턴
```
"적절한", "필요 시", "경우에 따라", "등", "기타", "추후", "별도 협의"
```

### 2. 데이터 ↔ 정책 정합성

Policy에서 언급한 데이터가 Data 문서에 정의되어 있는지 검증한다.

#### 검사 항목
- [ ] Policy에서 언급하는 **엔티티/필드명**이 Data 문서에 존재하는지
- [ ] Policy의 상태값(예: "승인", "반려")이 Data 문서의 상태 필드 정의에 포함되는지
- [ ] Policy의 조건(예: "재고 10개 이상")에 해당하는 필드가 Data에 정의되어 있는지
- [ ] Data 문서에 정의된 필드 중 **어떤 Policy에서도 참조하지 않는 고아 필드**가 있는지

### 3. 컴포넌트 ↔ 데이터 정합성

Component 문서의 UI 요소가 Data 문서의 필드와 매칭되는지 검증한다.

#### 검사 항목
- [ ] 테이블 컬럼의 **데이터 필드**가 Data 문서에 존재하는지
- [ ] 컬럼 타입(text, number, date)이 Data 필드 타입과 호환되는지
- [ ] 폼 입력 필드가 Data 문서의 필수/선택 여부와 일치하는지
- [ ] 셀렉트박스/드롭다운의 선택지가 Data 문서의 enum/상태값과 일치하는지
- [ ] 검색/필터 대상 필드가 Data 문서에 존재하는지

### 4. 액션 ↔ 정책 정합성

Action 문서의 유효성 검사/비즈니스 로직이 Policy 규칙을 반영하는지 검증한다.

#### 검사 항목
- [ ] Policy의 각 규칙에 대응하는 **유효성 검사**가 Action에 정의되어 있는지
- [ ] Policy의 조건(conditions)이 Action의 요청 파라미터 검증에 반영되었는지
- [ ] Policy에서 금지하는 동작이 Action에서 **에러 응답**으로 처리되는지
- [ ] Action의 에러 코드/메시지가 Policy 위반 사유를 명확히 전달하는지
- [ ] Policy의 권한 규칙이 Action에서 **권한 검사**로 구현되었는지

### 5. 화면 흐름 완결성

Wireframe 문서의 화면 흐름에 누락이 없는지 검증한다.

#### 검사 항목
- [ ] 각 상태(status)에 대한 **화면 표시**가 정의되어 있는지
- [ ] 상태 전이(예: 대기 → 승인 → 완료) **모든 경로**가 화면에 반영되었는지
- [ ] **빈 상태**(데이터 0건)의 화면 표시가 정의되어 있는지
- [ ] **에러 상태**(API 실패, 타임아웃)의 화면 처리가 정의되어 있는지
- [ ] **로딩 상태**의 표시 방식이 정의되어 있는지
- [ ] 목록 → 상세 → 수정 → 목록 **왕복 흐름**에 누락이 없는지
- [ ] 성공/실패 후 **리다이렉트 대상**이 명시되어 있는지

### 6. 도메인 간 연관성

서로 다른 도메인의 문서가 충돌하거나 누락된 연관 관계가 없는지 검증한다.

#### 검사 항목
- [ ] 상품 상태 변경이 클레임 처리 정책에 영향을 주는 경우, 양쪽 정책에 명시되어 있는지
- [ ] 도메인 A의 Action이 도메인 B의 데이터를 변경하는 경우, 양쪽에 참조가 있는지
- [ ] 공통(CMN) 정책이 각 도메인에서 올바르게 참조되는지
- [ ] 동일 엔티티를 다른 도메인에서 다른 이름으로 부르지 않는지 (용어 통일)
- [ ] 도메인 간 **상태 전이 의존성**이 문서화되어 있는지
  - 예: 클레임 승인 → 상품 재고 복원

---

## 실행 절차

1. 대상 범위의 모든 기획 문서 읽기
2. 문서 타입별 분류 (Policy, Data, Component, Action, Wireframe)
3. 각 검증 항목 순서대로 분석
4. `--cross-domain` 옵션 시 도메인 간 연관성 추가 분석
5. 결과 보고서 출력

## 출력 형식

```
🔍 기획 내용 검증: BO 상품 관리 (product)

1. 정책 완결성
  ❌ BO-PDM-001 규칙 3: 예외 케이스 미정의 — "복지포인트 부족 시" 처리 없음
  ⚠️ BO-PDM-001 규칙 5: 모호 표현 — "필요 시 관리자 승인" → 구체적 조건 필요
  ✅ BO-PDM-002: 정상/예외 모두 정의

2. 데이터 ↔ 정책 정합성
  ❌ BO-PDM-001: "할인율" 필드 언급 — BO-PDM-010 Data에 미정의
  ✅ BO-PDM-001: "재고 수량" — BO-PDM-010 stock_quantity 매칭

3. 컴포넌트 ↔ 데이터 정합성
  ⚠️ BO-PDM-020: 컬럼 "할인가" — Data 필드 미존재
  ✅ BO-PDM-020: 나머지 7개 컬럼 정상 매칭

4. 액션 ↔ 정책 정합성
  ❌ BO-PDM-030: Policy 규칙 2 "최소 주문 수량" — 유효성 검사 미정의
  ✅ BO-PDM-030: 필수 파라미터 검증 3건 정상

5. 화면 흐름 완결성
  ⚠️ BO-PDM-040: 빈 상태(0건) 표시 미정의
  ❌ BO-PDM-040: 상태 "반려" → 다음 액션 미정의
  ✅ BO-PDM-040: 목록 → 상세 → 수정 흐름 정상

6. 도메인 간 연관성
  ⚠️ 클레임 승인 시 상품 재고 복원 — 양쪽 정책에 미명시
  ✅ 공통 정책 CMN-001 참조 정상

---
결과: 통과 N / 실패 N / 경고 N
```
